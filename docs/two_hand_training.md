# Обучение последовательного переноса двух рук

Задача: `G1-Ladder-TwoHand-Motion`. Полный эпизод выполняет перенос левой
руки, устойчивое удержание, перенос правой руки и финальное удержание.
После первой руки нет reset, телепортации или отключения её захвата.
После каждой руки нужны минимум 3 секунды HOLD, в том числе 2 секунды
непрерывной устойчивости. После второй руки выставляется `finished` и
эпизод завершается штатным `success`. При нарушении устойчивости счётчик
обнуляется; таймаут HOLD — 8 секунд. Максимальная длина эпизода — 40 секунд.

Сохраняются вариация гравитации 0,97–1,03, слабые толчки и 20% чистых
эпизодов. Каждая рука получает отдельную проверку восстановления в HOLD;
при переходе между руками гравитация не пересэмплируется.

## Первый запуск с весами старой policy

Из корня репозитория в окружении `teleopit`:

```bash
python train_mimic/scripts/train_ladder.py \
  --task G1-Ladder-TwoHand-Motion \
  --warmstart logs/rsl_rl/g1_ladder_first_hand_motion/2026-10-02_18-08-19/model_10000.pt \
  --num_envs 1024 \
  --max_iterations 10000 \
  --second_hand_reset_probability 0.5
```

Размер наблюдений и архитектура сети сохранены. `--warmstart` строго
проверяет ключи и размеры actor/critic, загружает их веса и нормализаторы.
Оптимизатор, счётчик итераций и старое состояние curriculum не загружаются.
Сохранение checkpoint происходит каждые 1000 итераций и в конце запуска.

Если сигнатура первого эталона отличается, загрузка остановится до изменения
весов. У локального checkpoint и локально скомпилированного первого эталона
такая разница уже была обнаружена при сборе банка. Для намеренного переноса
весов между этими вариантами добавьте `--allow_warmstart_reference_mismatch`.
Это разрешение не делает эталоны идентичными: качество первого переноса нужно
проверить на новом запуске. Обычный `--resume` эту проверку не обходит.

Для нескольких GPU используются прежние `--gpu_ids 0 1 2 3`; число сред
задаётся по существующим правилам train_ladder.py. Проверка нескольких GPU
в данной реализации локально не выполнялась.

## Зачем половина стартов начинается со второй руки

При `--second_hand_reset_probability 0.5` половина сбросов начинает полный
эпизод, половина — правую руку из одной из восьми измеренных устойчивых поз.
Так обучение получает опыт второй руки даже до уверенного выполнения всей
цепочки. Внутри полного эпизода никакого сброса между руками нет.

- `0` — только последовательность из двух рук;
- `0.5` — смешанные старты, рекомендуемый начальный режим;
- `1` — только второй перенос для диагностики/отдельного обучения.

Успехи различаются в метриках `two_hand_success` (полная цепочка),
`second_hand_success` (эпизоды из банка), `first_transfer_complete`,
`started_at_second`, `active_transfer`. Эти поля являются индикаторами
эпизода; среднее при смешанных стартах не является условной долей успехов
только среди полных эпизодов. Причины отказов доступны также по руке и стадии:
`failure/right/prepare`, `failure/right/transfer` и т.д.

После освоения правой руки продолжайте новый checkpoint с вероятностью
сбросов на вторую руку 0, чтобы оценивать и дообучать полную последовательность:

```bash
python train_mimic/scripts/train_ladder.py \
  --task G1-Ladder-TwoHand-Motion \
  --resume logs/rsl_rl/g1_ladder_two_hand_motion/RUN/model_10000.pt \
  --second_hand_reset_probability 0 \
  --num_envs 1024 --max_iterations 5000
```

`--resume` предназначен для checkpoint новой задачи с тем же банком и
сигнатурой эталона. Его нельзя комбинировать с `--warmstart`.

## Эталон и перенос на кластер

Если проверка сообщает разное число geoms, выполните на кластере CPU-проверку:

```bash
python scripts/data/check_two_hand_geometry.py
```

Она печатает версии пакетов, добавленные/удалённые имена геометрии и различия
массивов. Полный список с телами и флагами столкновений сохраняется в
`outputs/two_hand_geometry.json`. Локальная проверенная сборка: MuJoCo 3.8.1,
mjlab 1.4.0, mujoco-warp 3.8.1, warp-lang 1.15.0; 229 geoms.

Банк версии 2 содержит исходные массивы геометрии MuJoCo. При несовпадении
побайтной сигнатуры они сравниваются с абсолютным допуском `1e-7` для
вещественных значений; целочисленная топология и размеры массивов должны
совпадать точно. Это допускает малый численный шум разных сборок, но не
смену лестницы. При отказе сообщение показывает поле, максимальное отличие
и первый различающийся элемент. Не отключайте эту проверку: сравните версии
репозитория, XML/mesh и MuJoCo, затем пересоберите банк при намеренной смене
геометрии. Старый банк без этих массивов при несовпадении сигнатуры отклоняется.
Добавление массивов меняет хеш NPZ: двухручные checkpoints со старой версией
банка не подходят для строгого `--resume`; warmstart от первой руки остаётся
доступен. Движения и измеренные стартовые состояния при этом не изменены.

`assets/motions/ladder_two_hand_bank.npz` — компактный банк (~600 КБ),
включённый в Git. Для обучения не нужны локальная папка `outputs/`, MJB
или исходный checkpoint, использованный когда-то для сбора поз (если
обучение идёт с нуля). Для warmstart нужен выбранный checkpoint.

Банк содержит восемь измеренных qpos/qvel и соответствующих эталонов правой
руки. При обычном переходе выбирается ближайшая по суставам стартовая поза;
Cartesian-цели привязываются к фактическим кистям, стопам и корпусу.
Начальная разница суставного эталона плавно сводится к нулю за подготовку,
так что базовая цель приводов непрерывна в момент перехода. Это ограниченное
переназначение целей около банка, а не IK для произвольной позы или лестницы.

Для второй руки геометрический критерий положения корпуса сравнивает COM
с его эталонным смещением относительно действующих опор. Исходная опорная
геометрия начала эпизода после первого переноса уже не подходит. Проверки
физических контактов, захватов, скорости и ориентации остаются обязательными.

Проверяются порядок суставов, частота и сигнатура геометрии модели.
При изменении робота или лестницы банк нужно перепроектировать и проверить.
Пересборка из существующих локальных данных:

```bash
python scripts/data/build_two_hand_bank.py
```

Можно передать другой банк через `--two_hand_bank PATH`. Его хеш входит
в сигнатуру checkpoint, поэтому подмена банка при resume не допускается.

## Видео и физическая диагностика

```bash
python train_mimic/scripts/record_ladder_video.py \
  --checkpoint logs/rsl_rl/g1_ladder_two_hand_motion/RUN/model_10000.pt \
  --frames 1800 --output outputs/two_hand_policy.mp4
```

Тип задачи определяется по checkpoint. Видеорежим всегда начинает полную
последовательность. Для нестандартного банка передайте тот же `--two_hand_bank`.

Физическое исполнение эталона приводами с нулевой поправкой policy:

```bash
python scripts/data/check_two_hand_runtime.py \
  --second_start 1 --no_disturbances --steps 650 \
  --output outputs/two_hand_physics.json
```

Для проверки старых весов добавьте `--checkpoint PATH`; при необходимости
используйте диагностический флаг `--allow_reference_mismatch`.

## Выполненные проверки и ограничения

Проверены фазовые переходы, опоры, удержание, непрерывность базовой суставной
цели, повторная проверка восстановления, совместимость warmstart и запись видео.
В GPU-rollout старых весов зафиксировано 18 переходов между руками без reset.
Это проверка механизма переключения, не успешного второго переноса.

Физическая проверка нулевой поправки без возмущений проходит подготовку,
отпускание и достигает TRANSFER. Она также выявила потерю опоры стоп во время
переноса: в 650 шагах на четырёх средах успешных эпизодов не получено.
Таким образом, кинематический эталон сам по себе динамической устойчивости
не обеспечивает; задача требует обучения корректирующей policy. Порог опор
для сокрытия этой проблемы не ослаблялся.

Пройдено 166 тестов. Короткий PPO smoke-run прошёл два обновления (384 шага
сред суммарно) и сохранил checkpoint; тот успешно загружен стандартным
скриптом записи видео, записаны 10 кадров. Это проверяет сбор rollout,
обновление сетей, сохранение и повторную загрузку checkpoint.
Длительное обучение и получение надёжной двухручной policy
не входили в эту проверку; результат двух smoke-итераций не следует использовать
как обученную модель.
